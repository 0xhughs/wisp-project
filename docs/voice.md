# Voice in Wisp

Voice uses the same companion and private Harness session as reasoning. Option–Space or the menu's Wake control starts one microphone utterance. Activate again to finish capture; while thinking or speaking, activation cancels the current operation. Mute disables both microphone activation and speech. Unmute never starts capture. Native action buttons remain the only tool approval mechanism; saying “yes” grants nothing.

Settings → Voice selects the recognition language and, independently, an installed speech voice and rate. Models selects reasoning. Voice uses the saved attached Local Ollama or DeepSeek model. Voice settings and the Wisp menu disclose the active route before capture; with DeepSeek, recognized text is sent to DeepSeek. No provider switch, connection test, fallback or retry happens automatically. The initial recognition choice is en-US, based on observed on-device support on the development Mac, not an inferred language preference. A language must report both available and on-device capable; unsupported languages cannot record and never fall back to Apple's server. The observed ar-SA route is not supported on-device on this Mac. Installed voices and support can differ by machine.

Wisp asks for its own microphone and speech-recognition permissions only after explicit activation. It never captures on launch, Settings navigation, Unmute, model Apply, playback or retry. Capture stops after at most 30 seconds; finalization has a 10-second deadline. Empty, partial, cancelled or failed recognition is not submitted. If release cannot be confirmed, Wisp refuses another operation until restart. Changing the audio device during capture stops the operation; check the device and restart before retrying.

Raw audio buffers are transient and are not saved. Recognized text becomes a user message in the private Harness session and may remain in its internal trajectory. It is not automatically curated into saved memory and is not shown as a chat transcript. Normal voice diagnostics contain phases, identifiers and counts, not recognized words or replies. Voice preferences and mute are nonsecret configuration in an owned atomic settings directory. Existing Models credential handling is unchanged.

The private voice pipe accepts only a bounded request with companion, engine generation and a unique utterance ID. The bridge selects its own session, rejects duplicate/foreign/stale requests, and admits only the attached supported reasoning route. Input and committed reply are limited to 4000 UTF-16 units and 8000 UTF-8 bytes; requests must fit 12000 bytes of encoded JSON within the 16 KiB pipe bound. Oversized input or output fails visibly; content is not silently truncated. A generation admits at most 1024 unique voice operations before it must be restarted. Unicode is decoded strictly across pipe chunks.

Speech waits for the matching user-message receipt, committed assistant message, completed turn and idle. Aborted or failed turns, reasoning blocks, tool payloads and abandoned attempts are not spoken. Live token streaming is not used. Actual synthesis callbacks drive speaking and completion. Cancellation retains ownership until release; a stop request before the start callback is not treated as a successful release. Cancellation can stop remaining output but cannot undo a tool effect already allowed and committed.

The implementation keeps macOS 14 as its package floor. Recognition uses AVAudioEngine and SFSpeechRecognizer with requiresOnDeviceRecognition only after checking supportsOnDeviceRecognition. Synthesis uses installed AVSpeechSynthesizer voices. Recognition and synthesis have distinct injectable interfaces and independent configuration. Carbon exclusive hotkey registration avoids keylogging and additional Accessibility permission; if registration conflicts, Settings explains the failure and native Wake remains usable.

API basis: installed SDK Speech/AVFAudio/Carbon headers and Apple's [on-device recognition property](https://developer.apple.com/documentation/speech/sfspeechrecognizer/supportsondevicerecognition), [speech authorization](https://developer.apple.com/documentation/speech/sfspeechrecognizer/requestauthorization(_:)), and [speech synthesizer](https://developer.apple.com/documentation/avfaudio/avspeechsynthesizer). Actual pinned Harness receipt/turn contracts are inspected at revision d347e703908d0406b7a7ef80e3a0e594d86b2215; the separate Wisp cancellation extension waits for actual agent idle.

## Verification boundaries

Native deterministic providers and typed-text bridge tests prove state, transport and local reasoning behavior. They do not establish microphone recognition accuracy or audibility. Required release evidence must identify an explicitly authorized physical microphone source, actual Wisp permission flow, real recognized request, corresponding selected model response and a listener's actual audible observation. A generated file, successful synthesis invocation or fake provider alone does not satisfy that gate. See the current slice evidence for remaining live obligations. No cloud speech, downloads, OS privacy reset, global routing changes, always-on listening, chat interface or new tool capability is included.

## macOS service readiness and development launch

Device support flags do not prove that the system speech service is enabled. On the tested Mac, the first instrumented task returned `kLSRErrorDomain`201 in4ms, before any audio buffer arrived. Apple's [recognition task error reference](https://developer.apple.com/documentation/speech/sfspeechrecognitiontask/error) identifies201 as Siri or Dictation being disabled, and102 as missing speech assets. Wisp reports these distinctly from silence. Choosing whether to enable Dictation or install required speech resources is a user/system decision; Wisp never changes those settings or silently selects a server recognizer.

Local development builds are ad-hoc signed after the full app bundle is assembled, binding its Info.plist usage descriptions and resources to `local.wisp.body`. Launch the app through the supplied LaunchServices runner, not by executing its Mach-O directly from a host application. The direct executable launch previously attributed a privacy request to its host and caused a TCC missing-description abort despite correct plist strings. This is local development signing; no distribution certificate, signing credential, notarization or publishing is performed. Apple's [code signing guide](https://developer.apple.com/library/archive/documentation/Security/Conceptual/CodeSigningGuide/Procedures/Procedures.html) describes bundle identity and signing; the installed `open` manual documents stream paths and application arguments.

The developer-only `desktop/tests/launch-native.py` uses a private temporary FIFO and precreated0600 output files so launchd does not need to open a protected Documents log before the app starts. It copies these owned logs to the requested proof directory on exit and removes its temporary files. Safe recognition diagnostics contain task success, final presence/length, elapsed capture time, categorical error domain/code and aggregate input buffer/frame counts plus a nonzero-sample flag. No sample, audio file, transcript, localized error payload or response text is added to those diagnostics. A nonzero sample alone would not establish intelligible speech or a working microphone source.

Recognition input and speech output have separate compatibility. The input list marks on-device availability; an unavailable choice cannot record. Output choices display their installed language, system quality category and novelty status. A different input/output language is called out before Apply. System quality categories are descriptive, not a promise of natural speech; installing Arabic output does not establish Arabic input support. Existing preferences are preserved, including a novelty voice if selected. A fresh configuration prefers an ordinary compatible installed voice; nothing is downloaded.

The one-call cloud voice verification allowance is an execution/testing constraint, separate from supported product routing. A real cloud spoken-loop proof still requires explicit physical activation, committed response and listener confirmation; a successful connection test alone is insufficient. Provider errors stay categorical in diagnostics and are never spoken as a reply; a failed owned turn tears down before another request. No credential inspection or new key-handling path is introduced.

Current development checkpoint: real participant speech has produced local and DeepSeek audible replies, and Option–Space interrupted speech. Voice quality remains a reported limitation (Samantha was described as robotic). Several physical cancellation, recognized-action approval and lifecycle checks are still pending participant availability. This is WIP evidence, not a shipped or independently accepted release; see [voice evidence](../evidence/07-voice.md).
