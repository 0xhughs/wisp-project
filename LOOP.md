# LOOP.md

## Authority and roles
- Work only through the authorized SLICES targets, preserving `AGENTS.md` and user authorization. Distinguish the **implementation target** (slices the user authorized to build and test) from the **acceptance target** (slices whose independent acceptance is required for release Complete). `Shipped` means independently accepted, not deployed.
- Coordinator is the sole writer of protocol files and archives. Builder writes application code/tests and returns proposed contract edits and proof. Reviewer reads and verifies; it returns verdicts and never implements fixes.
- Coordinator records Reviewer decisions verbatim. Only a valid independent Reviewer `APPROVE_IMPLEMENTATION` authorizes `Shipped` and an accepted-slice archive. `IMPLEMENTATION_READY` never authorizes those. Any participant may report a blocker or escalation; coordinator persists it.
- Use one active worker per checkout. A second coordinator must not start while ownership is unresolved. Record coordinator and worker identities in `BUILD.md`; stop/confirm the former owner before takeover.

## Execution setup
- Prepared is an unstarted pack, not a runtime blocker. Confirm the selected target and actual build authorization before the first worker dispatch; never interpret a repository URL or pack-authoring request as permission to execute the roadmap.
- Use distinct independent Builder and Reviewer agents. Initialize the Reviewer with project files and repository evidence, not Builder reasoning or a persona switch in the coordinator's context. Do not use the Builder as its own Reviewer.
- Before dispatch, persist the actual tool adapter, how it launches/checks/waits/stops workers, coordinator identity, and the worker role. Tool availability is not evidence that a worker was launched.
- If independent execution or verification of a **slice** is unavailable, preserve evidence, classify the gap (human test, missing platform, external resource, product decision, or implementation defect), and do not self-approve. Under the 2026-09-10 continue-eligible-work policy, missing human or platform evidence parks that slice; it does not by itself stop the run. Run-level Human required still applies when authority, retry/budget limits, or a decision that blocks all remaining eligible work is missing. No background scheduler is authorized by this pack.
- Source investigation may inform the initial contract; application implementation still requires an applicable independent plan approval. Subsequent proposal drafting is a no-code Builder phase.

## Dispatch and recovery
On the first authorized dispatch set SLICES Run status to `Running`. Mirror `Blocked` there only for a run-level temporary dependency. Mirror `Human required` there only for a run-level stop (authority, retry/budget limit, or a decision that blocks all remaining eligible work). Slice-level missing human or platform evidence does not change Run status to Human required; keep `Running` and record the slice as implemented-with-verification-pending or blocked with its class. After a run-level resolution restore `Running` or `Finalizing` as appropriate.

1. On resume, read live files and check recorded worker status, pending result, counters, snapshot identities, blocker and advance phase. Reconcile runtime activity before editing or dispatching.
2. Persist unique dispatch ID, role, phase, input identity and pending launch before starting the worker. Record returned agent ID. If launch was interrupted, discover or stop the old worker; never assume it did not start.
3. Builder receives the current contract and blockers. Reviewer receives current project files, candidate, baseline/diff and dispatch ID; its context is independent of Builder reasoning.
4. Wait for confirmed completion before changing ownership. Capture the result durably in BUILD `Pending result` (SLICES `Pending release result` for release reviews), then validate the dispatch, phase, input identity, and worker identity. Reject stale or duplicate messages as control events, without incrementing review-rejection counters.
5. Coordinator applies verdict, counters, event and `last consumed dispatch` together in one atomic `BUILD.md` replacement, then clears pending result. For release results, use the same atomic event/counter/consumed-ID transaction in SLICES Release evidence (including a pending-result field); reconcile BUILD advance phase afterward. Do not use a BUILD consumed marker alone to decide whether a release failure was counted. A crash before replacement leaves a replayable pending result; a crash after it cannot apply the verdict twice.
6. Workers never edit protocol files. Reviewer checks must not mutate candidate inputs; run mutating checks in an exact isolated copy. Unexpected external edits invalidate affected approvals. Do not overwrite unrelated user edits when persisting state.

## Snapshot and contract identity
Before first dispatch, record reproducible capture/recheck commands, coverage, exclusions and baseline in `BUILD.md`. Coverage includes source, tests, configuration, lockfiles, relevant assets and required untracked files. Exclude only named irrelevant/generated/dependency paths; Reviewer verifies coverage. Do not include secret values in proof.

A clean Git commit ID is sufficient only after confirming no relevant staged, unstaged or untracked content differs. Otherwise use a SHA-256 content manifest with sorted relative paths, file bytes, types, executable modes, and symlink targets. Detect additions and deletions by regenerating the covered file list. Record the manifest location and digest; without Git use this same manifest approach. The baseline must be available for comparison. Do not create commits merely to manufacture identity.

Contract identity covers the substantive `AGENTS.md`, product/target/criteria in `SLICES.md`, `BUILD.md` slice ID and Goal through Tests, and operational rules in `LOOP.md` and both role files. Include snapshot capture/recheck commands, coverage and exclusions in contract identity even though their values live in Loop state. Define exact extraction/hash commands; exclude only mutable bookkeeping (Proof, Review, Loop state except the snapshot-capture line, Status, Next, run status, release evidence, Implementation ledger, Verification backlog, and Shipped/Now/Later/Implemented-verification-pending placement). Preserve mapped slice content and target membership in the contract even if placement changes. Store manifests outside their own coverage. State-only writes must not invalidate approvals.

Reviewer independently computes identities before and after its checks and records both plus commands, results and artifact paths. Accept approval only if they match dispatch inputs and coordinator recomputation. Before Builder starts, validate plan approval against its baseline and contract. Before archiving or releasing, validate implementation approval against current candidate and contract. Changed contract -> `Proposed`; changed code after approval -> fresh plan review before implementation if baseline changed, or `Ready for review` for an otherwise unchanged completed contract. Never reuse stale proof. Intended Builder edits after valid plan approval produce the implementation candidate; they do not themselves require another plan review. For example, an external edit to an already-completed candidate with the accepted baseline and contract unchanged requires fresh implementation review, not another plan review.

## Implementation readiness versus acceptance
Track each slice as exactly one of: `unstarted`, `in progress`, `implemented with verification pending`, `accepted`, or `blocked`. Record the ledger in SLICES bookkeeping. Distinguish gap classes: missing human test; missing platform; missing external resource; required product decision; actual implementation defect; genuinely missing prerequisite.

- `accepted` requires independent `APPROVE_IMPLEMENTATION`, matching identities, and an immutable archive under `slices/`. That is Shipped for that slice.
- `implemented with verification pending` means available autonomous checks passed and remaining gaps are only recorded backlog items, not unfixed defects. It is not Shipped, not accepted, and not release-ready. Do not write an accepted-slice archive for it.
- `blocked` requires a recorded class and recheck. A pending human check is not automatically a dependency blocker for later slices. A genuinely missing prerequisite or unresolved implementation defect may be.
- Native code may be written on Linux. Mark it uncompiled and unverified unless an actual compatible runner checks it. Mocks, doubles and source inspection are supplemental evidence, not proof of native behavior.

Reviewer verdict `IMPLEMENTATION_READY` maps to implemented-with-verification-pending. Reviewer verdict `APPROVE_IMPLEMENTATION` maps to accepted/Shipped. Missing human or platform evidence alone is not `REJECT_IMPLEMENTATION` and is not a reason to repeat the same review of an unchanged candidate. Historical `HUMAN_REQUIRED` events remain verbatim records; a later policy may interpret them for run continuation without rewriting them or implying that acceptance gates passed.

## Continue eligible work
Identify dependencies across the authorized implementation target. When a slice reaches a verification gate this environment cannot perform, preserve its evidence in the consolidated verification backlog and continue the next eligible slice. Do not stop the entire project solely because a slice has outstanding human or Mac verification. Do not ask the authorizing user to verify features when they have stated they are unavailable.

A slice is eligible when: it is inside the implementation target; it is not accepted; it is not blocked on a product decision, external resource, permission boundary, or unresolved implementation defect that this increment must have; and each listed prerequisite is either accepted or implemented-with-verification-pending (not unstarted, and not blocked on a defect/missing implementation).

When building on an implemented but unaccepted prerequisite, record that dependency and the resulting integration/retest obligations in the ledger and in the later slice's contract. Do not assume the prerequisite works. Changes that would invalidate retained evidence are listed on each backlog item.

Recommended order after 07 is parked verification-pending (not a second Now): 10 (depends only on accepted 01/03/06) → 08 (record 07 retest; no model download without a resource plan) → 09 (record 07 retest; must not become a command-execution bypass) → 11 (after 10, or non-plugin MCP with a recorded 10 obligation) → 13 (record 07) → 12 (choose a supported demo skill when contracting; record 07/10/11 as required) → 15 (after 09) → 17 (implement on Linux only as uncompiled/unverified Windows sources; macOS tests do not prove Windows) → 16 (after 15) → 19 (after 13). Skip 18/20/21 until the required product decisions exist. Slice 14 is last among 01–14 because it depends on 01–13.

The expanded implementation target authorizes the existing slice definitions. It does not resolve explicitly undecided product behavior. Record genuinely required decisions, then continue unrelated eligible work. Keep permission enforcement, privacy, credential handling, cancellation guarantees and release gates intact. Do not disable safeguards to make tests pass. Do not publish, deploy, merge pull requests, or spend additional money unless separately authorized.

## State transitions
| From | Required event | To / next action |
|---|---|---|
| Proposed | Reviewer APPROVE_PLAN with matching inputs | Not started; Builder may start |
| Proposed | Reviewer REJECT_PLAN | Proposed; Builder revises proposal, then fresh plan review |
| Not started | Valid plan approval, Builder dispatch | Building |
| Building | Builder completes proof and stops | Ready for review; independent review |
| Ready for review | Reviewer REJECT_IMPLEMENTATION | Building; Builder repairs, then review |
| Ready for review | Reviewer APPROVE_IMPLEMENTATION with matching inputs | Shipped; coordinator advances (archive path) |
| Ready for review | Reviewer IMPLEMENTATION_READY with matching inputs | Implemented, verification pending; coordinator may park and select next eligible Now |
| Implemented, verification pending | Deferred evidence later yields APPROVE_IMPLEMENTATION with matching inputs | Shipped; coordinator advances (archive path) |
| Implemented, verification pending | Unresolved implementation defect found | Building or Proposed as appropriate; do not keep the ready label |
| Any unfinished slice | Missing human/platform evidence only | Park that slice verification-pending; run continues if other work is eligible |
| Any unfinished state | Temporary recoverable run-level blocker | Blocked; persist recovery fields; only the recorded recheck |
| Any state | Authority, retry/budget limit, or a decision that blocks all remaining eligible work | Human required; stop the run |

A revised proposal always returns to plan review. Builder may never alter accepted criteria to make a failure pass. If a necessary contract change is within existing authority, persist it and return to `Proposed`; otherwise escalate. Re-reviewing changed accepted code invalidates the old implementation approval and follows the same gates.

## Durable retry and budget policy
Default limits: 3 Reviewer rejections per slice; 2 consecutive repair attempts with no material improvement to failing evidence. Record user overrides here. Count both plan and implementation rejections, even when the reported gap changes. Plan approval, restart, worker replacement and phase change do not reset rejection count.

For each unique accepted review result, append event ID/dispatch, phase, verdict, input identities, acceptance gaps, evidence comparison and updated counters to `Review events`. Increment rejection count once for each REJECT verdict. After a repair, Reviewer compares evidence against prior open gaps: no material improvement increments no-progress; material improvement resets only no-progress. Initial rejection is not itself a repair. Missing comparison evidence must be resolved before another repair dispatch.

Check limits after recording the event and before another attempt. At either limit set run-level `Human required`, including reason and last evidence. Freeze final counter totals on implementation approval for the archive. Reset counters only for a new slice or explicit human authorization with a recorded reason. An unknown legacy count requires reconciliation, not an assumed zero.

`IMPLEMENTATION_READY` and slice-level missing human/platform evidence are not rejections and do not increment rejection or no-progress counters. Do not dispatch another implementation review of the same unchanged candidate solely because human or platform evidence is still missing.

Record an execution budget only if configured. Persist consumption using the available measurement source across resumes; inability to measure a required budget is a blocker. Check budget before dispatch and after result; when exhausted, preserve work and set run-level `Human required` before more work.

## Block and resume
Use `Blocked` only for a temporary dependency with a concrete safe recheck and bounded retry time/attempt limit. Save prior status, exact next action, blocker, evidence, recheck condition and deadline in `Loop state`. Keep counters, pending review result, approvals and dispatch records. Confirm any worker is stopped before resuming another.

On re-entry, perform only the allowed recheck. If unchanged, remain blocked without dispatching work or claiming background activity. If the limit expires or required permission/resource cannot be obtained, set run-level `Human required` when that resource blocks all remaining eligible work; otherwise keep the slice blocked with its class and continue eligible work. If resolved, validate identities and restore prior status/action, routing changed contracts/candidates back through the appropriate review gate. Clear blocker fields only after recording resolution. Unknown ownership cannot resume on timeout alone.

Run-level `Human required` resumes only after the specific missing decision/resource/authorization is supplied and evidenced. Record the resolution and restore the earliest unmet gate; retain counters unless explicitly reset. Do not escalate routine reversible implementation decisions. Do not treat a later-session batched human check as a run stop.

## Archive, advance and completion
1. After valid `APPROVE_IMPLEMENTATION`, persist `Shipped` and advance phase `archive pending`. Keep the approved identity and final counters. No worker may write code during advance.
2. Copy the accepted BUILD page to its stable archive path; never overwrite differing history. If the path already contains the same slice, verdict and approved identities, verify its substantive record and reuse it. A disagreement requires reconciliation. Persist `archive written` after verification; bookkeeping differences alone do not require a second archive. Never create that archive from `IMPLEMENTATION_READY` alone.
3. Add the slice once to Shipped in `SLICES.md`. If authorized implementation-target work remains, select exactly one next Now slice, record advance phase `next selected` plus `Next slice ID / draft` separately from the retained BUILD receipt ID, and dispatch a Builder draft-proposal phase for that next ID (no code edits). Only after archive verification replace BUILD with the next slice's Proposed page and zeroed counters. Plan review is required before code changes.
4. After `IMPLEMENTATION_READY` (not Shipped): persist the slice under SLICES `Implemented, verification pending`; seed or update the verification backlog; copy the unaccepted BUILD contract to `evidence/NN-contract-wip.md` labeled NOT ACCEPTED (this is not an archive); keep counters; select exactly one next eligible Now slice; dispatch a Builder draft-proposal phase (no code edits); replace BUILD with that next Proposed page and zeroed counters for the new slice. Do not write `slices/NN-*.md`. Historical review events stay verbatim. Record integration/retest obligations for work that builds on the unaccepted prerequisite.
5. After the last **acceptance-target** slice is accepted, set Now to `None — target complete` only if no further implementation-target work is eligible; preserve future Later slices; retain the last Shipped BUILD as a receipt; set advance phase `release pending`; and set run status to `Finalizing` only when the acceptance target and release gates are ready for independent review. Implementation-target slices 15–21 may still be in progress or verification-pending; they are not added to the 01–14 macOS first-release gates. No new Builder dispatch is allowed solely because BUILD remains Shipped.
6. Independent Reviewer checks applicable release gates against the final candidate and contract. Store verdict, identity and actual evidence in SLICES. With no gates, record `Not applicable` and verify target completion and approval freshness. Before success, coordinator rechecks those identities. Set run status `Complete`, advance phase `complete`, Next `None — target complete`, and stop. Do not declare Complete while required acceptance-target gates or unresolved implementation defects remain open. Verification-pending slices outside the acceptance target do not by themselves block Complete of the 01–14 release, but they also do not become release-ready by omission.
7. A gate failure cannot produce Complete: preserve its evidence, set run status `Needs repair`, and draft one Proposed repair slice only if it fits existing target/authority. Otherwise set run-level Human required. Give repair slices the normal review and retry gates; preserve previous archives. Bound repeated release repairs to 3 failed release reviews per target by default, recorded in SLICES; at the limit set Human required. Do not reset that count by creating another repair slice.

On interruption during advance, reconcile archive, Shipped entry, verification-pending placement, next selection and BUILD by slice ID and approved identities; continue the first unfinished step. Never rebuild accepted work merely because archiving was interrupted. If a draft was not persisted, regenerate only the next proposal. If completed-run inputs later change, invalidate Complete and re-review or propose authorized repair; do not overwrite the accepted archive.

Success requires: all **acceptance-target** slices accepted, Now empty or only implementation-target follow-on work remaining as recorded, matching final evidence, applicable gates passed or explicitly not applicable, no unresolved implementation defect or run-level escalation, and run status Complete. It does not authorize publishing, deployment, future scope, or continued background execution. `Implemented with verification pending` is never success of that slice.

## Verification backlog
Maintain one consolidated backlog in SLICES `## Verification backlog` (bookkeeping, excluded from contract identity). Do not create duplicate tracking files. For every deferred check record: slice and exact acceptance criterion; required platform, hardware, service, or human action; code revision and available automated evidence; exact command or short manual procedure; expected observable result; dependencies and changes that would invalidate retained evidence. Batch human checks for a later session. Do not repeatedly request the authorizing user's participation.
