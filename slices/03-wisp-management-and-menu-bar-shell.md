## Goal

Manage the existing running companion through a Wisp-owned native Settings window and macOS menu-bar item. Deliver all eleven navigation destinations, honest capability availability and working shell navigation/quit, sharing the accepted desktop controller and hidden runtime. This slice establishes management surfaces for later capability slices; it does not claim voice, model switching, memory or pet switching already work.

## Constraints

**Native architecture.** Continue Swift/AppKit/SwiftPM and the existing `.accessory` application policy/LSUIElement. Add a small `MenuBarController` owning `NSStatusItem`/`NSMenu` and a `SettingsWindowController` owning one ordinary titled, closable, miniaturizable, resizable `NSWindow`. Use standard AppKit navigation controls and layout, readable content with minimum sizing/scrolling so all sections remain accessible. No second application delegate, event loop or embedded renderer. Keep the existing `MascotPanel` non-key/non-main behavior. Explicit menu management actions use AppKit activation and `makeKeyAndOrderFront`; test their actual result because the SDK states activation is not guaranteed synchronously. No repeated activation timer or new accessibility permission workaround.

The existing `CompanionController` strongly owns both shell controllers alongside its one `EngineBridge`; actions flow through that application owner. Delegates/closures back to the owner use non-owning references where appropriate. A small typed `ManagementState` owns section selection and projects existing lifecycle state into immutable visible descriptions and action availability. Keep this finite shell model concrete; do not build speculative generic plugin/settings infrastructure. View components do not spawn engines or read route files. Capability unavailable is separate from runtime unavailable. Prefer disabled rows/buttons with visible explanatory text; do not rely only on tooltips to explain disabled actions. Change Pet/Model menu entries are enabled navigation actions with ellipses, whose destinations explicitly show unavailable selection.

**Lifecycle.** One retained Settings window is lazy-created on explicit request, retained when closed and reopened by its owner; no timer per section. AppKit close is not application quit. Closing the last management window must not terminate the accessory app. Route menu Quit through `NSApp.terminate` and the existing `applicationShouldTerminate` bridge-EOF cleanup rather than `exit`. On termination, disable further shell actions and release/remove menu/window resources once. Preserve existing forced-cleanup deadline and report forced cleanup separately; a normal menu Quit that requires force is not a claimed clean pass. Startup failure still creates the menu so users can inspect status and quit. Engine failure clears active body presentation while Settings stays navigable. The shell introduces no new lifecycle RPC; the accepted bridge and spike remain byte-identical unless a separately reviewed contract change becomes necessary.

**Scoped native state and display.** General's Show Companion only brings the existing panel into a reachable display frame and resumes its valid animation policy; it does not wake audio or transition to listening. Existing developer-only body hide/show/recreate controls stay private and may be reused in proof. General may describe the current ephemeral runtime attachment without promising relaunch persistence. Diagnostics displays fixed safe labels for readiness/failure, not raw event dictionaries, exception strings, paths, model responses, route URLs, identifiers or secrets. Internal detailed proof uses the existing developer-only bounded pipe channel, extended only with allowlisted read-only shell resource/status facts if necessary. Do not expose a production field for entering JSON, prompts or arbitrary operations.

### Proposal source evidence

Local inspection on this dispatch:

- `desktop/macos/Sources/WispBody/main.swift` already creates one accessory app/controller and runs one event loop; Info.plist declares LSUIElement. `CompanionController.swift` owns `EngineBridge`, body state, one session/runtime PID, SIGTERM/SIGINT handling, generation-safe presentation and application termination. Its `replaceBody` retains one panel and its controller; production launch has no developer stdin. This supports attaching shell controllers at the application owner rather than introducing a new runtime.
- `MascotPanel.swift` hard-overrides key/main eligibility to false and uses a borderless nonactivating floating panel. An ordinary separate Settings NSWindow is therefore necessary for keyboard-focusable management. Do not change the body to make it accept settings focus.
- `EngineBridge.swift` already projects known bridge events and owns anonymous pipes. `desktop/engine/body-bridge.mjs` supports only smoke/stop operations, gated smoke in developer mode, with one session ID per bridge and strict approval denial. It does not supply model inventory/voice APIs. This proposal requires no new bridge API or capability claims.
- `desktop/scripts/test-native.sh` and `NativeChecks.swift` establish the actual dependency-free assertion path; docs explain absent XCTest/Swift Testing in the installed command-line SDK. Retain that path rather than proposing an unavailable test dependency.
- Accepted02 GUI documentation already supplies an independent ClickTarget and test-only global input procedure, warns that app-targeted CUA clicks do not establish click-through, and records existing permission authority. This permits meaningful shell/body regressions without requiring product permissions.

Primary AppKit sources inspected:

- Installed SDK root `/Library/Developer/CommandLineTools/SDKs/MacOSX.sdk/System/Library/Frameworks/AppKit.framework/Headers/`: `NSStatusBar.h:27–28` declares creation/removal; `NSStatusItem.h:45–51` documents attached drop-down NSMenu and automatically supplied status button. Its later deprecated methods direct use to `button`/`menu`. Use native status item ownership instead of a custom overlay imitation.
- `NSWindow.h:393,422,438` supplies release-on-close, `makeKeyAndOrderFront`, and key eligibility. `NSApplication.h:219–231` documents `activate` (macOS14+) and explicitly warns activation may not be immediate or guaranteed. Thus real GUI activation/focus is an acceptance gate, not an assumption from API names. The existing package macOS14 declaration remains a build choice, not a support claim.
- Official Apple pages opened: [NSStatusBar](https://developer.apple.com/documentation/appkit/nsstatusbar), [Accessory activation policy](https://developer.apple.com/documentation/appkit/nsapplication/activationpolicy-swift.enum/accessory), [makeKeyAndOrderFront](https://developer.apple.com/documentation/appkit/nswindow/makekeyandorderfront(_:)). Their returned pages were JavaScript shells; detailed API claims above are grounded in the installed Apple SDK headers, not invented web-page content. No third-party source needed.

No new upstream runtime behavior is claimed; this proposal relies on inspected accepted Wisp sources and leaves the exact accepted pin/profile untouched. No build or GUI feasibility check was run in this no-code phase.
